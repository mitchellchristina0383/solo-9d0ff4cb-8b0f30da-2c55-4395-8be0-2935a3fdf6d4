# 部署完成通知 · 幂等送达演示系统

发布值班员通过网页向审计端发送「部署完成通知」。网络超时时无法判断对方是否已记账，
盲目重发又会产生重复记录。本系统用 **FastAPI + SQLite** 实现两端（各自独立数据库）、
并支持 **按环境暂停/恢复入账**：

- 相同「环境 + 发布号」的同内容重试，两端都只记一次；
- 同键不同内容 → **409 冲突**；
- 丢回执 / 接收端不可达 / 发送端重启 → 状态保持 **待核**，**绝不虚报成功**，
  恢复后凭接收端回执核对定案（已入账→已确认；未入账→回退待发送，可安全重发）；
- 审计值班员可在接收端网页**按环境暂停新部署通知**：暂停后新发布号被明确拒收（423，不落库），
  **已入账回执仍可查询**；暂停与在途入账交错时，先入账者必有可查回执，被拒收者不会随后自行入账；
- 暂停开关持久化于接收端 SQLite，重启后保留；写入失败则回滚、原状态不变；
- 发送端网页显示「暂停拒收」：拒收不等于已送达，也不等于可安全重发；恢复后须先核对再重试。

## 目录结构

```
├── docker-compose.yml      # 一键启动两端
├── sender/                 # 发送端（值班网页 + 发送/核对逻辑），端口 8000
│   ├── Dockerfile
│   └── app/{main.py, static/index.html}
├── receiver/               # 审计接收端（含暂停开关与故障注入），端口 8001
│   ├── Dockerfile
│   └── app/{main.py, static/index.html}
└── tests/
    ├── selftest.py         # 关键情形自测（仅标准库）
    └── run_local.sh        # 无 Docker 时的本地进程运行器
```

## 快速开始（Docker Compose）

```bash
docker compose up --build
```

- 发送端网页：http://localhost:8000 （填写环境、发布号、结果，提交并发送，查看接收状态与暂停状态）
- 接收端台账：http://localhost:8001 （实时查看已入账回执，并按环境暂停/恢复入账）

两端各持有一个独立 SQLite 库（compose 命名卷 `sender_data` / `receiver_data`）。
接收端的暂停开关保存在 `receiver_data` 卷内的 `env_pauses` 表，容器重启后仍然生效。

无 Docker 的本地环境（需 Python 3.11+ 及 fastapi/uvicorn/httpx）：

```bash
tests/run_local.sh start-all     # 两个独立进程 + 两个独立 db 文件
tests/run_local.sh stop-all
```

## 状态机（发送端）

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 待发送 PENDING | 本地已登记，未发送或已确认对方未记账 | 登记成功；核对时接收端明确无此记录 |
| 待核 UNCERTAIN | 已发出但回执缺失/对方不可达，送达与否未知 | 发送前落库；超时、连接失败、对方 5xx |
| 已确认 ACKED | 收到接收端内容一致的回执 | 发送响应 2xx 且内容哈希一致；核对命中 |
| 冲突 CONFLICT | 同环境同发布号在接收端已存在不同内容 | 发送/核对时发现内容不一致（需人工处理） |
| 暂停拒收 REJECTED | 接收端环境已暂停，该号被明确拒收且未入账 | 发送时收到 423；既非已送达，也不代表可安全重发 |

关键约束：**只有接收端回执能把记录变为「已确认」**。发送动作会先把「待核」落库再发 HTTP，
即使进程在发送途中崩溃，重启后也知道必须核对，而不是误报成功或误当未发。
「暂停拒收」只能由接收端 423 明确拒收产生；暂停期间核对遇到 404（对方无记录）**不会**把记录
改判为「待发送」，必须等恢复后再次核对确认无记录，才可安全重试。

## 演示场景

1. **正常送达**：网页填写 `prod / R2026-001 / 成功` → 提交 → 状态「已确认」，接收端台账出现一条。
2. **重复提交**：再次提交相同内容 → 发送端幂等去重、接收端仍只有一条。
3. **内容冲突**：同环境同发布号改选「失败」→ 提交即报 409 冲突，原记录不被篡改。
4. **入库后丢回执**：勾选「模拟接收端故障」再提交 → 状态变「待核」（接收端其实已入账）；
   点「重试」→ 接收端幂等去重，凭回执转「已确认」，仍只有一条。
5. **接收端不可用**：`docker compose stop receiver` → 发送/核对均保持「待核」（不虚报成功）；
   `docker compose start receiver` 后点「核对」→ 若对方无记录则回退「待发送」，可安全重发。
6. **发送端重启**：`docker compose restart sender` → 状态持久不丢；启动后自动核对所有待核记录，
   凭接收端回执结案（接收端不可达时保持待核）。
7. **按环境暂停入账**：接收端台账页输入 `prod` → 点「暂停入账」。此后发送 `prod` 的新发布号，
   发送端显示「暂停拒收」（接收端 423，不落库）；台账中**已有回执仍可查询**，同内容重试仍返回原回执。
8. **恢复后核对再重试**：接收端点「恢复入账」→ 发送端点「核对」确认对方确实无记录（回退待发送）→
   点「发送/重试」入账一条。暂停期间直接重发会被再次拒收，不会重复记账。

## API 摘要

发送端（:8000）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/notifications` | 登记（同键同内容幂等，同键不同内容 409） |
| GET | `/api/notifications` | 列表 |
| POST | `/api/notifications/{id}/send[?simulate=lose_response\|slow]` | 发送/重发（收到 423 记为暂停拒收） |
| POST | `/api/notifications/{id}/reconcile` | 凭接收端回执核对 |
| POST | `/api/reconcile-all` | 核对全部待核/待发送/暂停拒收 |
| GET | `/api/receiver-pauses` | 只读代理接收端暂停状态；不可达时返回 `reachable=false` |

接收端（:8001）：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/receipts` | 幂等入账；暂停环境的新号返回 423；body 可带 `"simulate":"lose_response"` 或 `"slow"` |
| GET | `/api/receipts?env=..&release_no=..` | 查询单条回执（404 表示无记录，附带该环境暂停状态） |
| GET | `/api/receipts` | 台账列表 |
| GET | `/api/pauses` | 所有已知环境的暂停状态 |
| GET | `/api/pauses/{env}` | 单个环境暂停状态 |
| POST | `/api/pauses` | `{"env":"prod","paused":true\|false}` 暂停/恢复；可带 `"simulate":"write_failure"` 验证失败回滚 |

## 暂停与入账的并发语义

- 暂停检查与「查重 + 插入」在同一个 `BEGIN IMMEDIATE` 写事务内完成：
  - 若入账事务先提交，其回执已可查询，随后的暂停不会回滚已确认记录；
  - 若暂停事务先提交，后到的入账请求在事务内看到开关，直接 423 且**不写入任何记录**；
  - 因而「先入账者必有可查回执，被拒收者不会随后自行入账」。
- 暂停只拦截**新发布号**。同键同内容重试返回原回执（200 + `deduplicated`），同键异内容仍 409。
- 暂停写入失败（含演示用 `write_failure` 注入）整个事务回滚：开关保持原值，接口如实返回 500 与原状态。
- 开关存于接收端 SQLite 的 `env_pauses` 表，重启后保留。

## 幂等与并发设计

- 两端均以 `UNIQUE(env, release_no)` 为幂等键，内容身份为 `{env, release_no, result}` 的 SHA-256；
- 写入路径 `BEGIN IMMEDIATE` 事务内「先查后插」，配合 WAL 与 busy_timeout：
  并发下同键只落一行，后到者走幂等返回或 409；
- 重发安全：接收端对同内容重试返回既有回执（200, `deduplicated`），不新增记录；
- 任一端写入失败都不会留下错误的成功状态：接收端写失败→5xx→发送端保持待核；
  发送端本地写失败→500 且无记录；拿到回执但本地更新失败→仍为待核，可靠核对补回。

## 自测

```bash
# Docker 模式（先 docker compose up --build）
python3 tests/selftest.py --lifecycle        # 含停接收端/重启发送端/重启接收端场景（钩子默认 docker compose）

# 无 Docker 本地模式
tests/run_local.sh test
```

覆盖：正常送达、同内容重试去重、同键冲突、丢回执后重发/核对、慢回执超时、
12 线程并发同内容、10 线程并发不同内容、接收端停机不虚报、发送端重启后待核持久与自动补核；
以及暂停/恢复相关：暂停期间新号 423 且不落库、已入账回执仍可查、同键幂等与 409 不受影响、
6 轮并发「入账 vs 暂停」交错（先入账必有回执、被拒收绝不入账）、暂停写入失败原状态不变、
接收端重启后开关保留、发送端显示暂停拒收且暂停期间核对不误判为可安全重发、恢复后核对再重试成功。
